A Descriptive text file describing all the Commands being broadcasted

>> The lesser the data transfer between Server and Client, the faster it all shall be

CLIENT:

*Commands
*CODES (Command Substitutent)
1. 1 (Typed: '/exit'): Closes Program and Instructs Server to Remove the Client as it is now offline
2. 2 (Typed: '/online'): Requests Server for a List of Online Members
3. 3 (Typed: '/Rooms'): Requests Server for a List of Online Rooms
4. 4 (Type: '/create'): Creates a New Room
5. 5 (Typed: '/room ivnite'): Invites a Client to the Room
6. 6 (Typed: '/room admin'): Adds a Member as a admin of Room
//Payload for Commands : ((Code, Arguments/Content), Type)


The Rest of Client Commands: The command isn't sent to Server, only the payload (message/data) is

*Types
1. msg: The containing message is to be broadcasted AS IT IS to Receivers
2. sys: The containing message contains Instructions(commands) to be acted upon by Server
3. hbp: Empty message, the type itself let's server know Client is alive
4. auth: The Containg message is a dictionary, containing all Credentials of User for Server to verify and Authorize



SERVER:

*CODES (Command Substituent):
1. 101 : To notify users when a client goes offline, Disconnecting Client being the Sender
2. 102 : To notify users to wait while Server closes their old session
3. 103 : To notify users that process is finished and they have relogged
4. 104 : To notify users that a new member has joined the room
5. 105 : To notify users that the room is now live
6. 106 : Room invitation arrived
7. 107 : Room made a member ADMIN

1. 201 : Invalid Credentials for Log In
2. 202 : Existing Username
3. 203 : To notify users that they are NOT an Admin of the Room
4. 204 : To notify users that they are NOT a Member of the Room (not invited) 
5. 205 : To notify users that the room already exists (same name)
6. 206 : Invited User already in room
7. 207 : Candidate User already admin

*Types
1. sys: System Message, returns Errors & Instructions [ like commands ]
2. auth: Confirmation of User's attempt to log on; Presence of 'sender' key makes it a [is Online] msg

*Destinations
1. /. : Every Online Client
2. /r<Room> : Everyone in room
3. /s : To the user who sent
4. *  : SPECIAL CASE
5.    : Username of receiver


DATA FIELDS:
sender ; receiver ; content ; command ; timestamp ; type

Client To Server -> Always Present: Sender, Content, Type 
                        Receiver (Present for msg, room)
                        Command (Present for sys)                        
                        Timestamp (Present for msg, room)

Server To Client -> Always Present: Content, Type
                        Sender (Present for msg, room)
                        Receiver (Present for None)
                        Command (Present for sys)
                        Timestamp (Present if originally existed)

REVERSE DICTIONARIES:
 Reverse of a Dictionary to avoid Dictionary Look ups [Value -> Key]

 1. user_sock & sock_room
 2. rooms & sock_room [Half Reverse]


INDEPENDENT CONCEPTS THATMAY BE CONFUSED TOGETHER:

1. Message Types & Receivers: 
        Type Signify PURPOSE, fully independent of Who Is to Receive it [Receiver & Destination are synonymous]
        This is why 'msg' is used for both DMs and Rooms, both are just Texts

2. System & Client Codes:
        System Codes are related to the display message
        Client Codes aren't for user display, they are purely to avoid Magic Values
