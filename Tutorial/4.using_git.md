# USING GIT

**NOTE, Git isn't used within Python, rather externally**

## Theory

Unlike the previous tutorials, this may be entirely new to you, as it is not language specific at all. Git is a that can be used by any software at all. It is a *version control* system, which allows you to:
1. Track Changes in Your Code, i.e., store your code history
2. Revert & Review those changes whenever your want 
3. Colloborate with Others. It is the most widely used tool for coding colloboration, multiple people can access and modify the same code
4. Work on new Features without tampering the original code

Now all of you here might noticed that, Git sounds awfully similar to GitHub, but they aren't all the same

### Git VS GitHub

Git: It Works Offline and is Local. It stores and tracks changes in your code on your local machine.
GitHub: Online Service for sharing code. It works with Git, so you can directly share your code from Local machine to GitHub. Though GitHub isn't the only one, other tools such as GitLabs and more exist for similar purpose.

*GitHub allows to Publish your local Work onto the Internet for your Team to Review and modify the code too. A way to work together on a Project. You can manually upload codes onto GitHub but that's unnecesary complex, this will teach you how to avoid losing progress in your code and how to store your code to the Online Repo of GitHub with just simple commands.*

## Git Terminologies

Some common words used around when talking of Git that you need to know, all of these are further explained in their own detailed section

| Term | Meaning |
|------|---------|
| Stage | Putting a File on Spotlight, to be finalized |
| Commit | To Finalize Something. To Save the current version of your Code as a Checkpoint |
| Checkout | To Revert back to your Last Checkpoint, your last commit |
| Branch | To work on new features without any of your changes affecting main code. Like a branch of tree, an alternate reality |
| Push | To send your code onto an Internet Repository |
| Pull | To download the latest code from the repository and merge with your current code |
| Fetch | To Download the latest code from the repository but not merge |

## Git Syntax

### COMMIT
 
When you make progress you don't wanna lose in a video game, you save at that location so you can revert back. That's what you do with commit. You save the current progress of your code locally in your computer, first you stage a file or files, that is, decide which files you want to save, then you commit.
The syntax is:

```bash
git add filename.format
git commit -m "Write Whatever you want here"
```

`git add ` This Stages the file, that is, chooses which files to commit. After this you type the location of whatever file you want to commit such as 'add.py', or 'read.txt'.
`git commit` Commits the files staged, that is saves their current progress so you can revert to them like a backup. You can give it a Description message to easily differentiate between different commits.

In Common use, we commit every code at once and together instead of specific files, to do that

```bash
git add .
git commit -m "Description of Changes"
```

Doing `git add .`, stages every single file that has any changes compared to last Commit and then the commit saves them. Really Helpful.

### CHECKOUT [REVERTING CHANGES]

Reverting changes can be done in 2 ways, RESET & Checkout; Reset should be avoided as one wrong slip could be bad and wipe your repo. Checkout is safer but Checkout is mostly used for Branches [more info on that later]. But to discard changes to a specific file:

```bash
git checkout -- filename
```

### BRANCH

A branch is like an alternate reality. Imagine your friend is working on the NPCs and Characters on a Spiderman game, while he does that you want to work on the Swinging Mechanic. In this scenario, your work is unrelated and hence you'll work on seperate code files, maybe 'characters.py' and 'swinging.c', but still you might have to modify stuff here and there to make it work, and *two people modifying and saving the same code can cause errors*

Hence you create a Branch, basically a copy of the Code, but any modification you do here won't affect the main branch, this way there's the 'MAIN/MASTER' Branch which has finalized code, and every feature under testing is in their respective branches,

```bash
git branch feature-name 
git checkout feature-name
```

`git branch feature-name` Creates a New Branch for you to work on that Specific Feature
`git checkout feature-name` Switches to that branch. This way you can switch between multiple branches and even branches and the MASTER branch to work on different stuffs together

*Branches are the essence of Colloboration*

### PUSH

Say you've made some signficant changes to your Feature, and even have multiple commits. You want others to be able to view and review your work now, instead of taking a screenshot or stuff, you can upload your code back into the Repository. *Push refers to putting your code from local machine to the Online Repo*

```bash
git push -u origin feature-name
```

This will Push your specific branch to the Repository for everyone to see

### PULL

When you create a branch, Every Code is copied, than you can do whatever with those codes or even make new files which won't affect the original branch AT ALL. Say you've made two new files and are doing all the code there for a long time, but by now the other members have improved the code in the rest of the files and finalized them.
*Pull refers to pulling the code from the Online Repo and Merging them with your code*. This way you can bring the latest finalized codes to ensure your code in the local machine stays upto date.

```bash
git checkout master         #Change to Master Branch
git pull origin master      #Pull all the changes from Master branch as they are the Finalized ones
git checkout feature-name   #Change to your Feature Branch
git merge main              #Merge the new finalized code into your own branch for most efficiency
```

### Minor Git Commands

1. `git status`: See Current changes
2. `git log`: See Commit History
3. `git diff`: Compare File Changes
4. `git branch`: See all Branches


## GIT TIPS

- Commit small, meaningful changes. Commit Often. Avoid crying in power outages
- Always write clear Commit messages so future you doesn't break his PC in confusion
- Avoid working on the MASTER BRANCH. Mess up there, mess up everywhere
